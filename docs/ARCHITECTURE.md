# Architecture

```
apps/web  ── REST, access token in memory + httpOnly refresh cookie ──┐
                                                                      ├── apps/backend ── PostgreSQL (Neon)
game      ── REST /play, token limited to one session ────────────────┘
packages/scenario     rooms, gates, themes, scoring constants, shared types
packages/validation   zod schemas, question validation, grading
packages/shared-types, packages/constants   roles and enums
```

The panels and the game are separate applications. They share no runtime state: the student panel asks the API to start a session and receives a one-time ticket; the game exchanges the ticket for its own token.

## Decisions

| Decision | Why |
| --- | --- |
| Existing NestJS + Prisma backend extended | The module layout was sound. Its gaps (retryable answers, client-supplied duration, missing rate limits, broad org checks) were closed. |
| One React app for three panels | Same stack as before, one design system, code-split by role. Permissions are enforced by the API only. |
| `game/` continued from the team prototype | Same folder, port and stack; the prototype scene was replaced by the full game. |
| Questions chosen on the server at start | `QuestionPicker` fixes one question per gate. The client never sees answers, hints or explanations before they are due. |
| Session configuration is a snapshot | Editing a campaign never changes a game in progress. |
| No timers in the API | It runs as a serverless function. Expired sessions are closed lazily; rate limits live in the database. |
| Rooms use plain requests, not sockets | A serverless function cannot hold a connection. Each game posts its position every 0.7 s and receives the others; the sprites walk between reports. |
| Guests are users with `isGuest` | They hold a token for one room. No membership, no sign-in, and they are left out of student lists and center statistics. |
| Teachers have a center, not a membership | `homeOrganizationId` is their center, so plan limits and student lists are not affected. |
| English text is the translation key | A missing translation shows English instead of an empty label. Tests compare keys and placeholders. |
| Students are users without e-mail | A personal code identifies them. `homeOrganizationId` says which center may edit the profile. |
| Art, music and maps generated by scripts | Original, consistent, reviewable, small (about 4 MB in total). |

## Tenancy

Every center-owned table has `organizationId`. `null` means official content. Controllers turn a request into a tenant only through `resolveOrg()` (center admins), `hostOrg()` (whoever opens rooms) and `studentOrg()` (students). Another center's record is answered with 404.

## Session flow

1. `POST /game-sessions/launch`: checks center, subscription, campaign window and group; picks questions; stores the snapshot.
2. The browser opens `GAME_URL#ticket=…`. The fragment is never sent to a server.
3. `POST /play/exchange` (once, within two minutes) returns the game token and the session.
4. `POST /play/answers` grades under a row lock. The same `requestId` always returns the first result.
5. `PUT /play/checkpoint` every 15 seconds and at important moments. Late requests are ignored by sequence number.
6. `POST /play/complete` recomputes everything from stored answers. A claimed escape without resolved gates is downgraded and flagged.

After a refresh the game reads `GET /play/session` and continues. A result that could not be sent is kept locally and sent on the next start.

## Without an account

`POST /play/guest` creates a throwaway guest (`User.isGuest`) and a session of the oldest official campaign that is not a level. From there it is an ordinary session: the browser holds no questions and no answers. `organizationId` is null, so no center sees it. Guests without a room are deleted after two days when the next guest starts.

## Room flow

1. `POST /lobbies` opens a room with a six-digit code, unique among rooms that are not finished (partial index).
2. `POST /room/join` with code and nickname returns a token with audience `lobby`. A signed-in student of the center joins with the own profile.
3. `POST /lobbies/:id/start` creates one session per player with the same questions behind the same doors.
4. Players launch through the usual one-time ticket. `POST /play/lobby` carries position and phrase id; nothing in it affects the score.
5. `POST /play/complete` stores the race time from the common start by the server clock. The room closes when the last player is done, when the host ends it, or when its time is over.

Standings: whoever reached the door first, fastest first; the others by progress, then points.

## Known limits

- Every player in a room has an own Invigilator and own doors: it is a race side by side, not one shared world.
- Positions are about a second old. This is enough for a school corridor, not for a shooter.

- The campaign builder configures rooms, questions, rules and texts. It is not a visual level editor.
- One map. New maps need a new `world/map.ts` and gate list.
- A game without signing in is not recorded. The game is not offline-capable for real sessions: answers need the server.
- Questions written by a center are shown in the language they were written in unless the center adds translations.
- There are no recorded voices. The game reads aloud with the voices installed in the browser; Uzbek is often missing.
